# 行程整理

先参考本轮最新共享行程、用户决定与原始资料，再查询缺失信息。使用当前实际可用的工具；Skill 描述工作规则，不代表应用已实现图片采集、视觉输入或相册功能。

## 引用与讨论

用户从行程选中文字添加到对话时，引用只是问题上下文，不是自动修改指令。结合用户本轮问题与最新共享行程，由 Pi 自行判断是否需要补充或修改；纯解释可只回答，需要变更时才调用 plan。保留未变动的安排、活动 ID、照片和来源，不能为了每轮都有更新而改写行程。

## 结构化行程

- 用 `plan` 更新完整行程，由 React 呈现；保留未被用户修改且仍有效的数据，不用摘要覆盖细节。以工具当前 schema 为字段依据，不生成 HTML 或页面脚本。
- 导入人工攻略时核对日期、逐日活动、交通、每晚住宿、备选和准备清单。区分原文、用户决定与 AI 建议，保留原文摘录及来源。
- 酒店安排不等于预订成功。住宿按每晚记录，只有预订证据才能标为 booked；不重复创建同一晚的住宿活动。
- 互斥备选用 optionGroup 表达，不串成必走路线。缺少时间、机场、房型等依据或资料矛盾时保留待确认事项；不补造精确数据。
- 使用当地时间，跨时区交通说明时区。准备清单是待办候选，不表示已经完成，不覆盖已有待办状态。
- 图文攻略和画板结合文字、图片、节点位置及连线解读。只拿到文字时说明读取范围，不声称已看图或理解全部空间关系。

## 地点与地图

- 经纬度须来自用户资料或实际查询结果，记录来源，使用 WGS84；不能凭地名生成坐标，不能把 GCJ-02/BD-09 当 WGS84。
- 区分具体地点与大致区域；没有依据就保留待定位。地点变化时同步核对旧坐标。
- 推荐候选可记录 recommendation.reason 和 recommendation.preferences，仅引用用户实际表达的偏好；候选不表示已经安排。
- 行程和地图引用同一地点资料。顺序连线不代表导航路线、交通方式或真实耗时；一次检索无结果也不证明地点不存在。

## 酒店与景点照片

用户需要照片或图文行程时，读取 [照片采集与核对](references/photos.md)。通过实际搜索和打开来源页面收集候选，核对对应酒店、分店、房型或景点，保留可追溯证据。酒店优先官网，景点参考官方旅游资料，也可从旅行平台、小红书原帖补充。

不能用生成图片或无关素材冒充地点实拍，也不能把“模型判断相似”写成真实性保证。未确认的图片保留不确定性。

图片展示目标：行程条目中展示，点击放大并查看来源；地图选中同一地点时复用相同图片资料。是否已呈现以工具写入结果和应用实际支持为准。优先使用 photo_candidates → save_photo，plan 通过已有 photoIds 引用缓存照片。采集失败时保留自动保存的待办，并用 journal 补充限制，不声称图片已加入行程。

## 完成核对

核对行程是否保留原始安排、备选关系、住宿状态和来源；区分已保存内容、待核对资料及当前工具无法完成的部分。只把旅行资料写入共享知识，不把工具日志或模型能力诊断写进去。
